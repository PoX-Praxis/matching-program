# 運用の決まり（OPERATIONS）

このリポジトリは、**引き継ぎ無しで、どの AI もここから現状と経緯を読み取れる**ように運用する。この文書はそのための決まりである。

---

## 0. 最初に読むもの

1. `docs/status.md`: いまの現状（1 ページ）
2. この文書
3. 作業に関係する `docs/decisions/`
4. 作業の指示書 `docs/instructions/<番号>.md` と、関係する前の報告 `docs/reports/`

詳しい棚卸しは `docs/status-report.md`、セキュリティの制約は `CLAUDE.md` にある。

## 1. 情報の持ち主

| 情報 | 持ち主 |
|---|---|
| 思想と背景（なぜ PoX をつくるか・場の考え方） | **Notion** |
| 実装・判断・現状（何をどう作ったか・何を決めたか・いまどうなっているか） | **このリポジトリ** |

- 食い違ったときは、次のとおりに扱う
  - 実装・判断・現状は、リポジトリを正とする
  - 思想・背景は、Notion を正とする
- Notion の本文をリポジトリに写さない。参照するときは、ページの名前を書く

## 2. 指示書と PR

- **1 指示書 ≒ 1〜数 PR。** ブランチは指示書（または PR）ごとに切り、main に直接 push しない。マージは squash
- **PR の最初のコミット:** 指示書を `docs/instructions/<番号>.md` に入れる
  - 本文は受け取ったまま入れる
  - §5 に当たる部分は伏せ、伏せたことを冒頭に書く
- **PR の最後のコミット:** 報告を `docs/reports/<番号>.md` に入れ、`docs/status.md` を更新する
- **複数の PR に分かれるとき:** 指示書は最初の PR、報告は最後の PR に入れる。途中の PR は、必要なら `docs/status.md` だけを更新する
- **追補・訂正:** 同じ番号に枝番を付けて足す（`<番号>-addendum<n>.md`）。元の指示書は書き換えない
- **番号:** 指示書の番号をそのまま使う（例: `66`・`65B-7`・`66C`）。番号の無い指示書は、短い英小文字の識別子にする（例: `repo-operations`）
- **マージの前:** CI（`pytest`）が通っていることを確かめる
- テンプレート: `docs/instructions/_template.md`・`docs/reports/_template.md`

## 3. 判断の記録（`docs/decisions/`）

- **判断をしたら、1 ファイル追加する。**
  - ファイル名は `docs/decisions/<3 桁の連番>-<短い英小文字の名前>.md`
  - テンプレートは `docs/decisions/_template.md`。一覧は `docs/decisions/README.md`
- **状態は 3 つのどれかにする。**
  - **確定:** 判断する人（KAORU）が確かめたもの
  - **下書き（要確認）:** 起こしたが、まだ確かめていないもの
  - **置き換え済み:** 新しい判断に替わったもの
- **置き換えるとき:** 古いファイルは消さない。状態を「置き換え済み」にして、置き換え先の番号を書く
- 理由のうち確かめていないものには、【推測】と書く
- 根拠になった指示書と PR の番号を書く
- 規則の変更（事前登録の変更・作動点の変更など）も、判断として記録する

## 4. 現状（`docs/status.md`）

- **1 ページ以内**にする。チャットに貼って現状を伝えるために使うので、短さを優先する
- 報告の最後のコミットで更新する
- 中身は次の 5 つ
  - いまの本体の構成
  - 動いているもの／閉じているもの／止まっているもの
  - 進行中の作業
  - 判断待ちの点
  - 最終更新日

## 5. リポジトリに入れないもの

次のものは、どのファイルにも書かない。指示書・報告・判断・コミットメッセージ・PR の本文も同じ。

- 個人の文（KAORU・PA など、実在する人が書いた文や、その人について書いた文）
- 生テキスト・根拠の本文・`evidence_span`
- 秘密（トークン・鍵・メールアドレス・`DATABASE_URL` の値など）
- 本人以外の数値（PA の gate など）
- 計測の個別の数値（対ごと・人ごと・文ごとのスコア）
- `local/` の中身（`local/` は `.gitignore` 済み）

これらは `local/` に置く。報告には、置き場所と識別子（ファイル名・sha256 など）だけを書く。

## 6. 計測（`docs/measure/`）

- **置くもの:**
  - 事前登録した規則
  - 判定（規則を満たすか）
  - 集計（曲線・AUC などのまとめ）
  - 使った材料の識別子（ファイル名・版・sha256・seed・モデルの id と revision・プロンプトのハッシュ）
- **置かないもの:** §5 に当たるもの（個人の文・個別のスコアなど）
- 計測ごとの文書に、次の 2 つを書く
  - **材料の置き場所**（例: 誰の手元の `local/66/` か）
  - **再現方法**（コマンド・引数・環境・所要時間の目安）
- **規則は計測の前にコミットする。**
  - 数値を見た後に変えるときは「規則の変更」とする
  - 変更は `docs/decisions/` と事前登録の文書の確認の記録に残し、判断する人の確認を取る
- 計測のスクリプトは `scripts/` に、計測のデータのうち公開してよいもの（架空の文など）は `scripts/probe_data/` に置く

## 7. 月 1 回の棚卸し

- **月に 1 回**、リポジトリを棚卸しし、`docs/status-report.md` を書き直す。冒頭に日付を書く
- 新しい棚卸しの冒頭に、**前回の報告との差分**を書く
  - 書くもの: 増えたもの・消えたもの・状態が変わったもの・片付いた判断待ち・新しい判断待ち
  - 前回の本文は git の履歴で見る（`git log -p -- docs/status-report.md`）
- 棚卸しの後に、`docs/status.md` と `docs/decisions/README.md` を合わせる

## 8. セキュリティの決まり

`CLAUDE.md` の「セキュリティの制約」を正とする。この文書と食い違ったら `CLAUDE.md` に従い、食い違いを報告に書く。
