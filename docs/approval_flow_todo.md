# 承認の動線に向けた申し送り（指示書27 §4 の記録）

指示書27（生成状態の表示と再試行の配線）では**触らずに記録だけ**した設計上の判断点。
次の「承認の動線」の指示書で扱う。ここは実装済みの内容ではなく、**未処理の TODO の記録**。

確定している承認の動線（目標像）:

```
下書き（通常DB・編集自由）
  ↓ 宣言と必要像をまとめて承認（個人＝確定 / コミュニティ＝合意）
台帳に記録（profile.structured + necessity.published）
  ↓
ベクトル化
```

---

## 4-1. サーバー側の必要像生成経路（fallback B）を塞ぐ

`POST /v4/seekers`（および v3 `/register` の dual-write）は、必要像フィールドを含まない JSON が
来ると、サーバーが `ANTHROPIC_API_KEY` で必要像を生成する経路（`_v4_async_job` の
`is_fallback=True`→`generate_necessity_v4`）を持つ。

**問題**: これは「本人が承認してから記録する」という確定設計に乗らない。本人が見ていない必要像が
**承認なしで保存・ベクトル化される**。①v4.3 は必要像を必ず出すため実質使われないはずだが、
経路としては生きている。

**対応（承認の動線で）**: fallback B を塞ぐ。必要像が無い入力は「下書き止まり」にし、
本人の承認を経てからサーバー生成 or 各自AI生成を確定させる。

現状（指示書27時点）: **塞いでいない。記録のみ。**

---

## 4-2. `needs_regeneration` の順序が逆

- **現状**: 「編集 → 再ベクトル化 → ズレの印（needs_regeneration）」。
  編集すると先にベクトルだけ新しくなり、必要像が古いまま `needs_regeneration` が立つ。
  さらに指示書27 で付けた「作り直す」ボタンは `retry` を叩くが、`retry` は
  **保存済み必要像があると再ベクトル化のみ**で、必要像そのものは作り直さない
  （＝古い必要像のまま `ready` に戻り得る）。これは暫定配線であり、真の作り直しではない。
- **確定設計**: 「編集 → **再生成 → 再承認** → 再ベクトル化」。順序が逆。

**対応（承認の動線で）**: 編集は意志・現状のみ可とし、必要像は直接編集させない。編集後は
必要像を再生成 → 本人が再承認 → ベクトル化、の順に組み替える。`needs_regeneration` の
設定タイミングもこの順序に合わせる。

現状（指示書27時点）: **順序は変えていない。記録のみ。**

---

## 4-3. 生成の再現性（`attempt_n`）

fallback 経路で必要像が未生成のまま失敗した場合、`retry` は生成からやり直す。
**LLM は非決定的**なので、同じ宣言から同じ必要像が出る保証はない。欠陥ではないが、
「どの生成結果を本人が承認したか」を一意に指せる必要がある。

**対応（承認の動線で）**: `necessity.published` に以下を持たせる。
- `attempt_n`: 同じ宣言に対する通算生成回数（破棄分を含む）。
- `source_snapshot_hash`: 生成元の宣言（意志・現状）の内容ハッシュ（穴A）。
- `generator_tag`: どの生成器が出したか（穴A）。

これにより「何回目の・どの宣言から生成した必要像を承認したか」が台帳から辿れる。

現状（指示書27時点）: **未実装。記録のみ。**

## その他、承認の動線であわせて実装する項目（指示書27 §6 より）

- `求めている`（seeking）を必要像の内容ハッシュに**平文で含める**。
- 手直しは**意志・現状のみ編集可。必要像は直接編集しない**（再生成 → 再承認）。
