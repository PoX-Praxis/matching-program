## 1. 契約（データの形）を固定する

### 1-1. カードの JSON

1組（見る人 × 相手）につき1つ。仕様 §2〜§4・§12-2・§12-3 を満たす JSON スキーマを、`schemas/` に置く。

- 目的ごと（`purposes`：見る人の目的 × 相手の文）と、逆の向き（`reverse_purposes`：相手の目的 × 見る人の文）
- 目的ごと：`ref`・見出し・種類（補完／共鳴）・`status`・① `meaning`（text・cites）・`elements`（`need_quote`・`offer_quote`・各 ref・`relation`・`must`）・`unknown`・`missing_must`
- 呼び方は記号（`{N}` 必要を出した側・`{O}` 文を出した側）。本文に名前や「あなた」を持たない
- カード全体：`status`（§12-2 の状態）・`show_reason`（監査用）・`as_of` と版（§12-3）・`output_digest`
- 引用（`citations`）：参照の欄と、原文の句

### 1-2. 向きの扱い

- 説明は向きごとに1つ（向き＝誰の目的 × 誰の文）。A の目的 × B の文 のカードの部分は、A の画面の本体と、B の画面の「A さんから見た B さん」の両方に使う
- データベースでは向きごとに保存し、画面で組み立てる

### 1-3. 描き方（レンダラ）

- **JSON から HTML を作る仕組み（レンダラ）を作る。画面に例文を直接書かない**
- レンダラは、読む人に合わせて記号を置き換える：
  - 画面1・2（見る人）：見る人＝「あなた」、相手＝「〇〇さん」
  - 画面3（申請を受けた人）：**一人称・二人称を使わない。両方ともユーザー名**
- 機械の確かめ（仕様 §6・§12-4）のうち、引用の実在・句の長さ・ラベル・呼び方・禁止の語・R1/R2 の述語・補充しないこと、は段階1でもレンダラの手前で通す（固定データでも、確かめに落ちたものは出さない）

---

## 2. 画面

### 2-1. 画面1：相手のプロフィール（候補）

- 置き場所：相手のプロフィールの「あなたの必要から見た、この人」の欄（65B-4）を、このカードに置き換える。上層の印は出さない（指示書67）
- 並び・形は仕様 §7-1 のとおり。**目的の並べ順はプロフィールの順で固定**（成否で並べ替えない）
- 末尾：「AI による説明です。根拠は二人の公開の文です。機械の確かめは正しさを保証しません。」と「補足する ›」
- 「補足する」：自分の文の言い換え（⑥の自分の側）についての補足。400字まで。送り先は §3
- ボタン「内容を確認して申請する」（§2-3）

### 2-2. 複数のアカウント（つながる・候補の一覧）

- 一覧では、相手ごとに短い形（名前・目的の見出し・① の1文）だけを出し、開くと画面1の全体
- 10件ずつの頁送り。並び順は中立（いまの相手の並び順。スコア・新しさ・成否で並べない）
- 説明が無い相手（`pending`・表示しない状態）は一覧に出さない。「準備中」と出さない
- 0件・1件・多件で崩れないこと

### 2-3. 画面2：申請

- 「内容を確認して申請する」の一つの操作。申請の文（任意・400字）は、これまでどおり
- 押した時点で、**見る人が読んだ表示（レンダラの出力）をそのまま**、申請の記録に添えて保存する（`render_digest` は §4 の鍵付き）

### 2-4. 画面3：申請を受けた人

- 仕様 §7-3 のとおり。申請者が読んだ内容を**再生成せず、そのまま**、ユーザー名だけで描く
- 「内容を確認しました（違う点があれば補足してください）」のチェックは**承認に必須**
- 「補足する」（400字まで）は、承認にも見送りにも添えられる（仕様 §12-1）
- 承認・見送りの動き自体は既存のまま

---

## 3. 補足と状態

- 補足つきで承認：補足を本人の言葉として保存し、接続の画面（合意した結果が出る箇所）で、説明と並べて出す
- 補足つきで見送り：申請者に届ける（受信箱）。見送りなので、説明の本文と補足は、届けた後に残さない（KAORU の決定：取り下げ・見送りは残さない）
- 画面1の補足：自分の文の言い換えについての補足として保存し、仕様の調整の材料にする（運営だけが読む。相手には出さない）
- 状態の出し分け（仕様 §12-2）：stale（承認時の説明として、日付つきで出す）・補足あり・deleted（本文は削除されました）

---

## 4. 保存とハッシュ（段階1で作る分）

- 申請に添えた表示（画面2）と、承認時に二人が見た表示を、本体の DB に保存する（台帳には書かない）
- 取り下げ・見送りのときは、その表示を消す
- `render_digest` は、サーバーの鍵付き（HMAC）で取る。鍵は環境変数で渡し、コードにもログにも出さない（POX_EMAIL_SALT と同じ扱い）。鍵の名前と、鍵を替えるときの扱いを報告する
- 合意の台帳イベント（`pair_digest`・正準形 a1）は段階2。段階1では、申請の記録に置く欄だけ用意してよい（空のまま）

---

## 5. 固定のデータ

### 5-1. リポジトリに入れるテスト用の合成データ（4ケース × 2人）

架空の二人で、仕様の形のカード JSON を作る（文は架空。実在の人の文を使わない）。

1. 補完（R1 または R2）で explained
2. 共鳴（R4 だけ）で explained
3. 疎（not_covered が主）
4. 古い・補足あり（stale・supplemented）
5. 同じ相手を2人の見る人から見て、説明が違うこと

### 5-2. KAORU × PA の評価用データ（リポジトリに入れない）

- KAORU が評価するのは、お手本（例1・例2）を仕様 v0.4 の形（②③は原文の句の抜き出し）に直したカード
- **このデータは本人たちの文を含むので、リポジトリに入れない。** 本番に読み込ませる方法を、コミットせずに済む形で提案し、**実装の前に報告して止まる**（例：運営用のルートからの読み込み・`local/` からの読み込み。トークンの扱いに注意）
- お手本の v0.4 形への書き直しは Claude が用意する。Code は形の確認だけをする
- 本番で表示するのは、**KAORU と PA の二人の間だけ**（フラグと許可リストで閉じる。§6）

---

## 6. フラグ

- `POX_EXPLANATION`：`off`（既定）／`allowlist`（指定した利用者の組だけ）／`on`
- 段階1の本番は `allowlist`（KAORU と PA だけ）。許可リストの持ち方を報告する
- `off` のとき、画面と API は今と同じ（「あなたの必要から見た、この人」はいまの表示のまま）

---

## 7. テスト

1. カード JSON がスキーマに通る／通らないものを弾く
2. レンダラ：画面1・2 は「あなた」「〇〇さん」、画面3 は名前だけ。本文に「あなた」が残らない
3. 目的の並びがプロフィールの順で、成否で変わらない
4. 確かめ（引用の実在・句の長さ・ラベル・R1/R2 の述語・禁止の語・呼び方・補充しない）に落ちた部分が出ない
5. 画面2 で保存した表示が、画面3 でそのまま（呼び方の置き換えだけで）出る。再生成していない
6. 画面3 で確認のチェックが無いと承認できない。見送りは確認なしでできる
7. 補足つきの承認で補足が保存され、接続の画面に出る。補足つきの見送りで申請者に届き、本文と補足が残らない
8. 取り下げ・見送りで、保存した表示が消える
9. `render_digest` が鍵付きで、鍵が無いと起動を止める（`allowlist`・`on` のとき）
10. `POX_EXPLANATION=off` で、今と同じ
11. `allowlist` で、許可リストの組以外には出ない
12. 0件・1件・多件・stale・補足あり・deleted の表示が崩れない
13. 上層の印が出ない（指示書67 と矛盾しない）

---

## 8. 段階1の合格の条件（KAORU と PA が評価する。仕様 §12-9）

1. 一度読んで意味が分かる
2. 根拠が1回の操作で開け、引用が原文から来ていると分かる
3. 補完と共鳴が区別できる
4. ⑤ が「公開の文の中に無い」と読め、責められている感じがしない
5. 画面1→2→3 が迷わず通る。「補足する」が見つかる
6. 同じ相手を2人から見て、それぞれ違う説明が正しく出る
7. 0件・多件・stale・補足あり の状態が破綻しない

（PA は v4 なので、画面の読みやすさと流れの評価に使う。内容の正しさの証拠にはしない。KAORU×PA は「二人の相互の表示」の確認であって、第三者に開ける関門ではない）
