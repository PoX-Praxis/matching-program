## 4. 画面の整理

### 4-1. 登録画面

- rev5 の JSON を受け付け、`種類`・`説明への使用` を検証する（値の外は弾く）
- **B（v5r5-B）の場合だけ**、保存の前に確認の画面を出す：目的ごとの必須（最大2つ・0も可）・目的の種類・「縛られているもの」の使用の可否を、本人が選ぶ。A は対話の中で選び済みなので、読み取りの表示だけでよい
- 登録時の同意：「利用規約・プライバシーポリシー（接続の説明を含む）に同意する」の**1つのチェック**にまとめる。説明の同意だけの別の欄はやめる（§4-3）

### 4-2. マイページ

- 「欠かせない要素」の切り替え（65B-7）を**外す**。必須は表示だけにし、「変えたいときは、構造化し直してください」と添える
- 「目的の種類」の選択（指示書69 §4-4）を**外す**。表示もしない（相手にも本人にも。説明の出し方にだけ使う）
- 「縛られているもの」の使用の切り替え（指示書69 §4-3）を**外す**。構造化の答え（`説明への使用`）を使う
- 「接続の説明」の同意の欄を**外す**（§4-3）
- 構造化し直す入口（AI で作り直した JSON を貼る）は今のまま

### 4-3. 同意の一本化

- 新しく登録する人：登録時の1つのチェック（§4-1）で、プライバシーポリシー 6-2（接続の説明）を含めて同意する
- すでに登録している人（KAORU・PA）：次のログインで一度だけ、「プライバシーポリシーが更新されました（接続の説明について）。同意する」を出す。`terms.accepted` に、ポリシーの版を記録する
- 同意するまで、その人の説明は作らない（指示書69 のまま）。取り込み分（KAORU×PA）は出し続ける
- 指示書69 の「説明の同意だけの版（2026-11-expl-v1）」は、ポリシーの版に置き換える。すでに記録した `terms.accepted` は消さない（過去の記録として残す）

### 4-4. つながる

- 「照合の結果」の節（「照合中…」と、上層の保留の文言）を**外す**
- 「説明のある相手」を、見出し **「つながる意味が見つかった相手」** にする
- 冒頭の説明「あなたの目的ごとの必要像から、いま噛み合いそうな相手を照合します。詳細・承認は各プロフィールから。」を、次に改める：
  ```
  あなたの目的と、相手の公開の文から、つながる意味が見つかった相手を示します。詳細と申請は、各プロフィールから。
  ```
- 「申し出が届いている相手は、ここではなく受信箱に出ます。」は残す

### 4-5. 登録者一覧

- 1人ごとに、**表示名（ハンドルがあれば `@ハンドル` を添える）と、目的の見出し（向かう先）だけ**を出す。目的が無い人（v4）は一行紹介だけ
- 一行紹介の長文・「目指していること」・「必要としている相手」の全文は、一覧からは外す（プロフィールを開いて読む）
- 表示名で絞り込む欄は残す。並びは今のまま（スコアで並べない）

---

## 5. 説明の生成への反映（指示書69 との関係）

- 目的の種類：構造化の `種類` を使う。無い（rev4 以前）ときは、仮の規則（指示書69 §4-4）
- 「縛られているもの」：構造化の `説明への使用.縛られているもの` が true のときだけ使う。無いときは使わない
- 指示書69 で作った「目的の種類の別の表」と「縛られているものの許可の版」は、構造化の値に置き換える。すでにある値は、構造化し直すまでの間の仮の値として読むか、消すかを報告する

## 6. テスト（例）

1. rev5-A・rev5-B の JSON を受け付け、`種類`・`説明への使用` を検証する。値の外は弾く
2. rev4 以前の JSON も今までどおり受け付け、`種類` は仮の規則、`説明への使用` は false になる
3. B の登録で、確認の画面で選んだ必須・種類・使用の可否が保存される。必須3つ以上は選べない
4. マイページに、必須・種類・縛られているものの切り替えと、説明の同意の欄が無い
5. 既存の利用者に、ポリシー更新の同意が一度だけ出る。同意すると `terms.accepted` に版が記録され、もう出ない
6. つながるに「照合の結果」の節が無く、「つながる意味が見つかった相手」の見出しと新しい冒頭の説明が出る
7. 登録者一覧が、表示名（とハンドル）と目的の見出しだけになる
8. プロンプトのファイルの sha256 が、報告の値と一致する。登録画面がそのファイルから読み込む
9. 説明の生成が、構造化の `種類` と `説明への使用` を使う（指示書69 のテストを合わせる）
