## なぜ作るか

指示書76 順2 で、Nemotron は線 2（拾えた）で 0/24 だった。原因は、モデルが「求められている像」と「相手が書いたこと」を混ぜ、関係（R1/R2）を付けまちがえ、話題だけ近い組をつないだこと。

新しい設計（生成仕様 v1.0）では、**LLM は句を抜き出すだけ**にし、**応えるかどうかは機械の規則（照合の表）で決める**。表で誤りを落とせなければ、プロンプトをどう直しても直らない。そこで、LLM とつなぐ前に、**表だけ**を測る。

## 0. 変えないもの

- 本番の画面・照合（nomic の候補）・記録・フラグ。本番には何も出さない
- **LLM を使わない。**借りた GPU も使わない（費用 0）
- **表の中身（関門・種類・互換・概念・条件）を、Code が変えない。**表で落とせない組・落としすぎる組は、報告するだけ。直すのは Claude と Sakana
- v2 と 48 組は見ない。使わない
- 数値を画面と公開 API に出さない
- KAORU と PA の文をリポジトリに入れない（今回の材料は、すべて架空の文）

## 2. 作るもの

### 2-1. 形態素解析

- fugashi＋unidic-lite。版を固定する（requirements に版を書く。辞書の版も記録する）
- 句ごとに、語の辞書形・品詞・活用・助動詞の並びを取り出す

### 2-2. 照合（表の §8 の順）

入力は、必要の句（1 つ）と、相手の文（1 つ）。

1. **相手の文を句に分ける**：読点や「〜て」「〜し」の連用の切れ目で、述語ごとの句にする。句ごとに 2〜6 を見て、どれか 1 つの句が最後まで通れば、その句を組の句にする（LLM の抜き出しの代わり）
2. **関門**（表 §1）
3. **句の種類**（表 §2）と、**必要の型**（原則 v1 §1）の**互換**（原則 v1 §2）
4. **述語の種類と枠**（表 §3）
5. **対象の領域**（表 §5・§6）
   - nomic は、対象の句どうしだけを比べる補助。線は、60 組と gates_v1 の負例が 0 になる、いちばん低い線にする（機械的に決める）。線と、その決め方を報告する
6. **必要の文の条件**（表 §7）
7. 関係（R1〜R4）と、［C］の種類（経験・継続・現職・申告・所有・使える立場・同じ関心）を決める

**判定は 3 値**（合う／合わない／分からない）。分からないは落とす。

**どこで落ちたか**を、組ごとに記録する（関門の名前・種類・述語・枠・領域・条件のどれか）。

### 2-3. ［B］の名詞化（生成仕様 v1.0 §6-1）

必要の句を、「〜人」で終わらない形に、機械で名詞化する（例：「〜してきた人」→「〜してきた経験」・「〜できる人」→「〜できること」・「〜に関心がある人」→「〜への関心」）。規則は Code が案を作り、60 組の必要の句（12 文）すべての結果を報告に載せる。

### 2-4. 型の ①（生成仕様 v1.0 §6-2）

通った組について、型の ① の文を作る。

> {N}が求める「［B］」について、{O}は「［offer_quote］」と書いています（［短い名前］）。

60 組と gates_v1 で通った組すべての文を、報告に載せる（架空の文だけ）。

## 5. 成功の条件

1. 60 組と gates_v1 のすべての組について、通ったか・どこで落ちたか・関係と［C］の種類が出る
2. 表の版・道具と辞書の版・nomic の線が、記録の一式に入る
3. 同じ入力で、同じ結果になる（決定性）
4. 既存のテストが通る

**失敗したときに結論すること**
- 句に分ける段で、句の切り方が文によって崩れるとき：崩れた文を挙げて報告する（LLM の抜き出しに任せる部分になる）
- 表の文書だけでは、データのファイルに写せないところがあるとき：推測で埋めずに、挙げて報告する

## 6. テスト（例。番号は今の続きで付ける）

- 関門ごとに、gates_v1 の負例が落ちる。元の組は通る
- 「見る」が、対象で消費と支援に分かれる（S23 と S12）
- 軽い動詞（担当する）が、対象で種類に分かれる（S01・S41・S51）
- 「教える」の枠で、内容が違えば落ちる（S04・G28）
- 概念表で、言葉が重ならない正しい組（S16・S26・S31・S46）が通る。領域が近いだけの負例（G24〜G27）が落ちる
- 使える立場（S17・G30）・継続（G20）・現職（G21）が、決めた［C］の種類になる
- 結果が、同じ入力で同じになる
