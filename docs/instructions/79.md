## なぜ測るか

1 組の説明に時間がかかりすぎる。精度を保ったまま縮める手（B・C を後回し・ラベルの出力を二回に分ける・遠い候補を先に外す・同時に動かす・前置きの再利用・考える深さ）を選ぶ前に、**時間が何に使われているか**を知る必要がある。

**今回は、新しく走らせない。** すでに手元にある記録（`local/` の出力・ログ・ジョブの記録・リポジトリの架空の組の出力）から、数だけを取り出す。

---

## 0. 変えないもの・守ること

- **モデルを走らせない。** Hugging Face Jobs も、ローカルの推論も起動しない（費用 0）
- コード・プロンプト・確かめ・設定を直さない
- **KAORU・PA の文を、報告・リポジトリ・ログに出さない。** 報告に書くのは、数・時間・ラベルの名前・部品と組の番号だけ。部品の文・key の語・fails_if の文・説明の文は書かない
- 報告は `docs/reports/` に置く。`local/` の中身はコミットしない
- 数値は報告にだけ書く（画面と公開 API には出さない）
- トークン・鍵・メールアドレスを書かない
- 記録に無い数を、推測で埋めない。無いものは「記録なし」と書く

## 1. 何を取り出すか

### 1-1. 記録の目録（まずこれ）

次の回について、何が残っているかを一覧にする。

| 回 | 物差し |
|---|---|
| 4 回目（部品＋候補＋ラベル） | KAORU×PA |
| 5 回目（ラベル v0.3） | KAORU×PA・最小対 50 組 |
| v06（選ぶ・まとめる） | KAORU×PA |

回ごとに、次の有無を書く：出力の JSON・vLLM のログ・リクエストごとの usage（入力と出力のトークン数）・開始と終了の時刻・ジョブの記録（状態と時間）・使った設定（モデル・vLLM の版・reasoning_effort・最大トークン・同時の数・前置きの再利用の有無）。

一番そろっている回（v06 のはず）を、§1-2 以降の中心にする。

### 1-2. 時間の内訳（1 組あたり）

| 項目 | 取り出すもの |
|---|---|
| 起動 | ジョブの開始からモデルが読み込み終わるまで |
| ラベルの段 | 向きごとのリクエストの数・時間 |
| 選ぶ・まとめるの段 | リクエストの数・時間 |
| 機械の段 | 部品・候補・関門・確かめ・カードの組み立て（分かれば） |
| 合計 | 1 組の始めから終わりまで |

vLLM のログに入力の速さ・出力の速さ（tokens/s）があれば、それも書く。

### 1-3. トークンの内訳（リクエストごと）

- 入力のトークン数（そのうち、部品の一覧の分と候補の一覧の分。分かれば）
- 出力のトークン数を、**考える部分**（reasoning）と **JSON の部分**に分けて
- 記録に usage が無いときは、保存してある入力と出力の文字列を、**gpt-oss の tokenizer だけ**で数える（モデルは動かさない）。数え方を報告に書く

### 1-4. 候補とラベルの内訳

- 部品の数：1 人あたり、役目ごと（necessity・purpose・bound・experience・offer・state.have・state.can_type・interest・文脈）
- 候補の数：向きごと・A・B・C ごと
- ラベルの数：A・B・C ごとに、ラベルの種類ごと
- 「応える」とされた組（same_kind・relational・partial・same_interest）の数と、そのうち関門・確かめを通った数と、選ぶ段で選ばれた数

### 1-5. 出力の JSON の中身の内訳（一番知りたいところ）

ラベルの段の JSON の部分を、候補ごとに分けて tokenizer で数え、次の割合を出す。

| 区分 | 数える |
|---|---|
| A の irrelevant・topic_only・unclear | 候補の数・トークン数 |
| A の「応える」（same_kind・relational・partial・same_interest） | 候補の数・トークン数 |
| B の候補すべて | 候補の数・トークン数 |
| C の候補すべて | 候補の数・トークン数 |
| 欄ごと | link・basis・key・missing・counter・fails_if・決まった形（括弧・キーの名前など）が、それぞれ何トークンか |

ここから、次の 3 つを**計算だけで**見積もる（走らせない）。

1. B と C をラベルの段から外したときに減る出力のトークン
2. 1 回目は link だけ・2 回目は「応える」にだけ key と fails_if、としたときの出力のトークン
3. JSON のキーを短くし、空の欄を省いたときの出力のトークン

見積もりには、「考える部分が同じだけ減るかは分からない」と書き添える。

### 1-6. 最小対 50 組（5 回目）

記録があれば、1 組あたりの入力・出力のトークン数と時間を、KAORU×PA と並べて書く。部品の数が少ない組で時間がどう変わるかを見るため。

## 3. 失敗したときに結論すること

- 時間かトークンの記録が足りず、内訳が出せないときは、**足りない項目と、それを次に測るために記録に足すもの**（例：リクエストごとの usage と時刻を保存する）を書いて止まる。走らせ直しはしない（走らせるかは KAORU が決める）
- ジョブの出力を消していて残っていないときは、そう書く
