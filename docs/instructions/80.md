報告79 で、1 組 約 9.7 分の内訳が分かった。起動が 43%、ラベルの段が 48%（N_by_O 83 秒の後に O_by_N 194 秒を順に動かしている）。時間は、ほぼ出力のトークン数で決まる（毎秒約 99）。

## 0. 変えないもの・守ること

- **プロンプトを直さない。** `prompt_label_v0.3`・`prompt_select_v0.1` のまま。sha256 が変わらないことを確かめる
- 生成の設定を変えない：モデル・重みの版・vLLM v0.33.0・温度 0・seed 0・reasoning_effort medium・最大トークン・`VLLM_BATCH_INVARIANT=1`・**前置きの再利用は切ったまま**
- 部品・候補・関門・確かめ・カードの組み立てを変えない
- KAORU・PA の文は、決まり（2026-11-19）のとおり非公開のジョブでだけ処理し、終わったら出力を消す。手元では `local/` だけに置く。報告・リポジトリ・ログに文を出さない
- 架空の組（`data/explanation_bench/synthetic_v1.json`）は使ってよい
- 鍵・トークンを会話・リポジトリ・ログに入れない
- 数値は報告にだけ書く

## 1. 何を変えるか

### 1-1. ラベルの段の二つの向きを、同時に送る

- N_by_O と O_by_N のラベルのリクエストを、同時に送る。両方が返ってから、選ぶ・まとめるの段に進む（今の順と同じ）
- vLLM の同時に動かす数を、2 件以上にする（何件にしたかを記録する）
- 選ぶ・まとめるの段は、今のまま（1 組の中では、ラベルの後）

### 1-2. 何組かを、1 回の起動でまとめて作る

- 1 回のジョブ（1 回の起動）で、作る予定の組を順に処理する。起動の約 250 秒を、組の数で割る形にする
- 別の組どうしを同時に送れる形にする（同時の数は設定で決める。§2 で確かめるまで、本番の既定は「1 組ずつ」）
- 推論先の窓口（`hf_jobs` ↔ `local_http`）の形は変えない。どちらの推論先でも同じ動き方にする

### 1-3. 時間を記録する（報告79 §7 で足りなかったもの）

- リクエストごと：送った時刻・最初のトークンの時刻・終わった時刻・入力と出力のトークン数（考える部分と JSON に分けて）
- vLLM のログ：起動の内訳、入力と出力の速さ
- 機械の段の時間
- 記録には、数と時刻と番号だけを残す。文は残さない

## 2. 確かめること（ここでだけ、モデルを走らせる）

1 回のジョブの中で、次の 3 つを同じ設定で走らせて比べる。

| 回 | 中身 | 組 |
|---|---|---|
| a. 順に | 今のやり方（1 件ずつ） | KAORU×PA・架空の組 3 つ |
| b. 同時に（1 組の中） | 二つの向きを同時に。組は 1 つずつ | 同上 |
| c. 同時に（組どうしも） | 二つの向き＋別の組を同時に | 同上 |

- 架空の組 3 つは、部品の数がなるべく違うものを選ぶ（多い・中くらい・少ない）
- 比べるもの：ラベルの JSON・選ぶ段の JSON・組み立てたカード。**一字まで同じか。**考える部分が記録に残るなら、それも比べる
- KAORU×PA は、`local/` にある v06 の出力とも比べる（環境の違いで v06 と違ったときは、a と b・c が同じかを正とする）
- 費用と時間を記録する

## 3. 成功の条件

1. a・b・c の出力が、すべての組で一字まで同じ
2. プロンプトの sha256 が変わっていない
3. 1 組あたりの時間（起動を除く）が短くなる。目安：約 330 秒 → 約 250 秒（ラベルの段は、長いほうの向きの時間になる）
4. c で、何組かを作ったときの 1 組あたりの時間（起動を割ったもの）が出ている
5. §1-3 の記録がそろっている
6. 報告に、KAORU・PA の文が入っていない

## 4. 失敗したときに結論すること

- **b で出力が変わったとき：** この vLLM の版では、同時に送ると結果が変わる。二つの向きは順に送るままにする。§1-2（起動をまとめる。組は 1 つずつ）と §1-3 だけを入れる
- **b は同じで、c で変わったとき：** 組の中の同時だけを入れる。組どうしは 1 つずつにする
- どちらの場合も、どこで何字目から違ったか（番号だけ）を報告して止まる。設定をいじって合わせ込まない
