## 3. Issue の写しを作る

### 3-1. 写し

`docs/reports/issues_snapshot_2026-11-25.md` を作る。**Issue だけ**（PR は §3-2 に分ける）、開いているもの・閉じたものの両方。

| 欄 | 中身 |
|---|---|
| 番号 | #NNN |
| 題 | Issue の題そのまま |
| 状態 | open／closed |
| ラベル | 名前だけ |
| 作った日・閉じた日 | 日付だけ |
| つながる PR | Issue から分かる PR 番号（無ければ空） |

- 並びは番号の大きい順
- 先頭に、数だけの要約：Issue の合計・開いている数・閉じた数・写した日時（JST）

### 3-2. 開いている PR

- 開いている PR の一覧（番号・題・ブランチ名・作った日）。下書きかどうかも書く

### 3-3. 開いている Issue の見立て（Code の言葉で・1 件 1 行）

開いている Issue ごとに、次の 3 つのどれかを付ける。本人の文は書かない。

| 印 | 意味 |
|---|---|
| 残っている | まだ手が付いていない、または途中 |
| 済んでいそう | `docs/reports/` の最新や、マージした PR で済んでいるように見える（どの報告・PR かを書く） |
| 古そう | 決定ログで方向が変わり、もう本線ではないように見える（どの決定かを日付で書く） |

- **Issue を閉じない・ラベルを変えない・コメントしない。**見立てを書くだけ。閉じるかは KAORU が決める
- とくに、プロジェクトの指示にある #181〜#194 は、全部について一行ずつ書く

### 3-4. 作り直す道具

- `scripts/ops/issues_snapshot.py` を作る。GitHub の REST API で §3-1・§3-2 の表を作る（§3-3 の見立ては作らない）
- トークンは環境変数（`GITHUB_TOKEN`）から読む。リポジトリに書かない
- 次からは、KAORU が頼んだときにこの道具で写しを作り直し、日付を変えた新しいファイルにする（古いものは残す）
- テストは、偽の API の応答で表が作れることだけを見る

4. §3-3 の印ごとの数（残っている・済んでいそう・古そう）
