# 照合（つながる）の仕組みと運用の注意（指示書55・55-2）

## 1. 埋め込みのモデルは 1 つ

- 「検索層」と「照合層」の区分は**実装に存在しない**（この語は使わない）。埋め込みのモデルとバックエンドは
  **1 組だけ**で、プロフィールのベクトルも必要像のベクトルも同じモデルで作る。
- 違いは **prefix だけ**（nomic: 意志どうし・必要像＝`search_query:`、現状＝`search_document:`）。
- 本番（2026-09-30 の inventory で確認）: **backend=nomic・model_tag=nomic-emb-v2・768 次元**。
  **照合も nomic で動いている**。qwen3 は未導入。

## 2. 設定の解決（`src/embedding_config.py`）

| 変数 | 未設定のとき |
|---|---|
| `POX_EMBED_BACKEND` | `stub`（意味の無い擬似ベクトル）。**本番（`POX_DEBUG` なし）では起動しない** |
| `POX_EMBED_MODEL_TAG` | `qwen3-embedding-0.6b-d1024`（次元と prefix の決定に使う） |

- 解決は「環境変数 → コードの既定」の 2 段だけ。起動ログに
  `[embedding] backend=… backend_env_set=… model_tag=… model_tag_env_set=… dim=…` を出す。
- **タグの規則**: 実バックエンドのタグは `<backend>-` で始まる（既存の `nomic-emb-v2` はこの形。改名しない）。
  backend とタグが食い違う設定は起動時に止める。**stub のタグは常に `stub-d<次元>`**で、実タグと混ざらない。
- **stub の間は照合の結果を出さない**（「照合の準備中です」）。他の画面は動く。

## 3. 照合の母集団と入口

- 照合は**同じ model_tag・is_active** の行どうしだけ。タグが割れると母集団が分裂するので、
  **モデルの切替は一括**（全員の再ベクトル化が済んでから env を切り替える。次元が変わるなら別表）。
- 方向 A（自分の必要像 × 相手の現状）と**方向 B（相手の必要像 × 自分の現状）**を、同じ式・自分の α・β で
  評価し、**どちらかの総合が内部閾値（`MATCH_ENTRY_THRESHOLD`＝0.70・**暫定**）以上**なら「照合の結果」に入れる（式は §12）。
  b（補完）単独では切らない。閾値は内部定数で、画面にも API にも出さない。
- 除外: 自分／本人と紐づいていない id／必要像が無い人／既に接続済み・申し出中の相手。
- 並びは中立（id 順）。数値・順位・件数は出さない。軸は「意志が近い」「足りないところを埋める」
  （双方向なら「足りないところを互いに埋める」）と、**両者の公開本文**だけで説明する。
- 登録者一覧（`GET /seekers`）も v4（`profiles_v4`）が正。旧 v3 `seekers` は読み取り専用で残す。

## 4. 運用の注意

- **`ledger_v4` の `match_ranked`（2026-09-30 時点 546 件）は信頼しない。** 指示書55 PR-A 以前は照合 API が
  未認証で、誰でも任意の人について照合を実行できた。この期間の記録は利用状況として扱わず、読む API も作らない。
- **自宅 PC の nomic が照合の単一障害点。** 不達の間は新規登録・編集の埋め込みが失敗する
  （本人面では `error` と「準備中」を区別して出し、再試行できる）。照合そのものは既存のベクトルで動く。
- 必要像レコード（`necessities` の query ベクトル）にも `model_tag` を記録する（指示書55-3）。別タグのベクトルは
  照合に使わない（人起点へ戻る）。列を足す前に作った行（空）は現行タグとして扱うので、切替の前に作り直すこと。

## 5. モデル切替中は照合しない（テスト 185）

- 「**ベクトル化済みなのに現行タグの有効行を持たない人**」が 1 人でもいる間は、「照合の準備中です」を返す。
- 「他のタグの行がある」では判定しない（旧タグの行は切替後も `is_active` で残るので、止まり続けてしまう）。
- まだ一度もベクトル化されていない人（準備中・失敗）は数えない（1 人の失敗で全員の照合が止まらないように）。
- 件数は inventory の `vectorized_without_current_model_tag` で見られる。

## 6. 閾値の尺度

`MATCH_ENTRY_THRESHOLD = 0.70` は **cos ではなく `g(cos) = (1 + cos) / 2` の加重べき乗平均（総合）**に対する値。
全チャネルが同じ値なら cos ≈ 0.4 に相当する（無関係を除く、緩い下限）。

## 7. 説明文のテンプレート（connect.html の実文）

各カードは「軸の名前」1 行＋理由の行（軸に応じて 1〜2 行）。理由の行は**次の形の固定文**で、
LLM の生成文は使わない。本文は両者の公開本文そのまま（サーバーで切り詰めない。表示は 2 行で丸める）。

| 軸（画面の名前） | 理由の行 |
|---|---|
| 意志が近い | `あなたの意志『{自分の意志}』× 相手の意志『{相手の意志}』` |
| 足りないところを埋める（自分の必要像側） | `あなたの必要像『{自分の必要像}』× 相手の現状『{相手の現状 4 スロットを " / " で連結}』` |
| 足りないところを埋める（相手の必要像側） | `相手の必要像『{相手の公開の必要像}』× あなたの現状『{自分の現状}』` |
| 足りないところを互いに埋める | 上の 2 行（自分の必要像側 → 相手の必要像側）を並べる |

- どちらかの本文が空（相手の必要像が非公開など）なら、その行は出さない（軸の名前だけになる）。
- 「×」で 2 つの本文を並べるだけで、**どの語・どのスロットが対応しているかは示していない**（並置）。
  チャネルの単位（意志どうし・必要像×現状）までは対応しているが、現状 4 スロットのどれが効いたかは出せない
  （ベクトルがスロット単位で無いため。判定書 §4-2「v1 は軸の名前まで」）。

## 8. 未認証で書き込めるルート（許可リスト）

CI（`test_t193_no_unexpected_unauthenticated_write_routes`）で固定している。効果のある書き込みは次の 3 つだけ。

| ルート | 理由 |
|---|---|
| `POST /auth/request` | ログインメールの送信（ログイン前に呼ぶ） |
| `POST /auth/logout` | ログアウト |
| `POST /ledger/anchor` | `X-Anchor-Token` 必須（外部スケジューラ）。不一致は 404 |

ほかに 410 を返すだけの閉鎖・凍結ルート（`POST /seekers`・凍結した intent 系 6 本）がある（書き込みはしない）。
これ以外の書き込みはすべて `login_required`。監査の読み取り（`/ledger/audit/*`）は GET で、`X-Anchor-Token` 必須。

## 9. テスト専用の `POX_TEST_ALLOW_STUB`

テスト（conftest）だけが設定する。本番（`POX_DEBUG` なし）で stub を拒否する起動ガードを、テストの間だけ外す。
**本番では設定しない。** Render（`RENDER` が自動で立つ）でこの変数が立っていたら起動しない。

## 10. 承認の場面の根拠（指示書55-5 §1）

- 受信箱・マイページの接続カード・プロフィールの承認欄に、照合の結果のカードと同じ根拠（軸の名前＋両者の
  公開本文）と、受け取った申し出の文を出す。共通部品は `templates/_match_reason.html`。
- 根拠は **その場で再計算**する（`GET /api/connections/reason?with=`）。申し出の時点の根拠は保存しない
  （本文の更新が反映される・新しい表や台帳を持たない）。申し出・承認待ち・接続中の相手に限る（任意の人の
  照合を引けると、照合の結果の除外や横断禁止を迂回できるため）。入口の閾値では切らない（説明のため）。
- 申し出の文の入力欄は、プロフィールからの申し出とつながるページのカードの両方にある（任意・400 字）。

## 11. 意志の下限（指示書55-5 §4）— **撤去**（指示書56）

- `#126` で入れた `WILL_FLOOR_G`・`will_requirement`（`gate_s × (1 − gate_u)`）と、それに連動した「互いに埋める」の
  意志条件は**撤去**した。全文 cos は無関係なペアでも意志の軸が高く出る（実測 `ga = 0.800`）ため、その上に
  ゲートを建てても無関係を通す。**同じ目的のゲートを二重に置かない／新しいゲートも作らない**（段2〜3 で再設計）。

## 12. 総合の式（指示書56 段1「計算の整理」）

```
総合A = M_0([g(a), g(b)], [α, β])    a: 意志 × 意志 / b: 自分の必要像 × 相手の現状
総合B = M_0([g(a), g(d)], [α, β])    d: 相手の必要像 × 自分の現状
入口:  総合A ≥ 0.70 または 総合B ≥ 0.70（平均しない）
互いに埋める: g(b) ≥ 0.70 かつ g(d) ≥ 0.70（両方向が別々に）
```

- **γ は廃止**（照合の計算に使わない）。上限 0.5 で総合にほぼ効かず、意味も二重だった。生成時に
  `derived_necessity.gamma` 列へ保存する値は、過去の版と同じ形を保つためだけに残る（照合では読まない）。
- **p は 0 固定**（幾何平均）。`p_sharpness` は必須文が無いので段2 まで使わない。
- **補完は方向ごとに判定し、平均しない。** 「私はあなたが必要だが、あなたは私を必要としていない」という
  最も普通の片方向の組が、平均で薄まって落ちないように。
- **c を判定から外した（設計からのずれの記録・テスト 204）**: Embedding v4 の設計では **c は「必要像 × 意志」**
  だった。**実装は `will_passage`（意志の passage 表現）どうしの対称な類似度**で、実測でも両方向が同値
  （KAORU × ProjectAequitas で 0.572 / 0.572）。無関係なペアで最も高く出る（0.848）など識別力も無い。
  段3 では「向かう先」の文どうしの比較がこの役割を引き継ぐ。
- **閾値 0.70 は暫定**（`MATCH_ENTRY_THRESHOLD`）。実測で、全文 cos は「意味の一致」ではなく「文体・話題・
  書き手の近さ」に反応し、**閾値では関係のある組と無い組を分けられない**（無関係 0.800 > 関係あり 0.762）。
  判定の再設計は段2〜3（目的ごとの必要像・与え像・文単位）で行う。
- 照合の結果が 0 件のときは、**本人の側の理由だけを 1 行**出す（必要像がない／まだ照合できる相手がいない）。
  相手ごとの除外理由は出さない。

## 13. 照合の段2〜3（指示書57・①v5）

### 受信・保存
- ①v5 の JSON（＋本人の語り）を受け取り、**検証規則 10 項目**を通す（`src/v5.py` の `validate`）。通らなければ
  保存せず、理由を 1 行で返す。語り（`supporting_material.生テキスト`、または登録画面の別欄）は**本人のみ・
  根拠の引用の検査にだけ使い、照合には使わない**。
- **目的の id はサーバーが振る**（`pur_…`。不変）。①の `purpose_id` は対応付けのヒント。再構造化のときは
  確認画面で「前のどの目的の続きか」を本人が選ぶ（既定は順番どおりの提案）。対応が取れない目的は新しい目的、
  前の目的のうち選ばれなかったものは、その必要像に `necessity.retired`（目的と過去の版は残る）。
- 台帳（**新しい型は作らない**）:
  - 宣言 `profile.structured` … 任意キー `canon_version: "p2"`（無いもの＝c1）。p2 の対象は目的の
    {purpose_id, 向かう先, 手段}・関心・現状 4 つ・背景／一行紹介／要約文。
  - 必要像 `necessity.published` … **目的ごとに 1 件**。任意キー `purpose_id`・`offer_hash`。ハッシュは **c3**
    ＝ H(必要像の文の配列 [{文, 必須, 型}] ‖ 数値 {gate_s, gate_u, alpha, beta} ‖ commit(根拠, salt) ‖ offer_hash)。
    置換の鎖（prev_necessity）と churn は**同じ目的の直前**と比べる（別の目的を置換しない）。c1・c2 の行は
    そのまま読める（`necessities.canon_version` で規則を選ぶ）。
  - 与え像 … 通常DB（`offers`・版ごと）。**台帳には書かず、offer_hash を各目的の必要像の c3 に含める**
    （ピン留め・案 A）。与え像だけが変わっても、同じ①の出力の各目的の必要像が新しい版として書かれる。
- 文単位ベクトル（`sentence_vectors`）: 必要像の文（query）と与え像の文（passage）を個別に埋め込む。
  1 人あたり最大 目的 3 × 5 文＋与え像 5 文＝20 本（全文ベクトル 4 本は互換のため残す）。

### 照合・表示（`src/matcher_v5.py`）
- **目的ごと**に「その目的の必要像の文 × 相手の与え像の文」の全対を比べる。**型をまたぐ**（型は使わない）。
- 判定は `judge(need, offer)` 1 か所（いまは g(cos) ≥ 0.70・暫定。手作業検証で含意判定に差し替えうる）。
  ある向きが成立＝判定を通る対が 1 つ以上あり、**必須の文はすべて**通る対を持つ。
- 補完A（自分の目的の必要像 × 相手の与え像）か補完B（相手の目的の必要像 × 自分の与え像）のどちらかで
  入口を通す。**両方なら「足りないところを互いに埋める」**。共鳴（意志どうしの cos）は使わない（56）。
- 表示は目的ごとにグループ化。根拠は**引用の対（1〜2 組）**「◯◯の『…』に、△△の『…』が応えています」。
- **v4 互換**: 与え像の無い人は「目的 1 つ・与え像の代わりに現状」で照合する。マイページに
  「与え像が未設定のため、現状で照合しています」を常設（照合のたびには出さない）。

### 接続
- 申し出に `purpose_id` と、申し出た時点の版の参照（自分の必要像 `necessity_ref`・与え像 `offer_ref`）を
  保存する。**冪等は「相手 × 目的」**。成立時の `a_ref`/`b_ref` の `necessity_hash` は各自の申し出の目的の
  最新の必要像の event_hash。
- 承認の画面の根拠は**版の参照から再計算**する（根拠のコピーは保存しない）。
- 申し出中の相手は、照合の結果から（目的によらず）外す。

### 手作業検証
- `scripts/manual_pairs.py`（開発用・本番に入れない）で 2 人の文の全対を CSV にし、人の判定と突き合わせる。
  合格条件は 2 つ（無関係な組を出さない／噛み合う組を落とさない）。協力者は実在の別の人。
