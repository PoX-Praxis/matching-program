**推測で補完した箇所**
- **プロンプトの埋め方:** 仕様のプロンプトの `{N の目的・…}`・`{O の与え像・…}`・`{目的の参照・…}` の 3 か所を、型付きの JSON で置き換える
  - 記号 `{N}`・`{O}` はそのまま残す
  - sha256 は置き換える前のファイルの中身で取る（段1 `92f1a316…`・段2 `19f3bdc7…`）
- **出すかどうかは機械が決める（仕様 §4-1）:**
  - モデルの `status` は、not_covered と言ったときだけ従う（落とす方向にだけ）
  - explained かどうかは、確かめを通った組と、入力の欠かせない要素の印から決める
  - 欠かせない要素の印は、モデルの出力ではなく入力から取る（§12-4 の 13）
- **① の確かめに落ちたとき:** その目的は出さない（段階1 の check() と同じ扱い）
- **as-of:** 二人の読む欄の内容ハッシュにした（`h:<sha256>`）
  - プロフィール全体や版の番号ではなく、説明が読む欄だけ（仕様 §8-2 の考え方に合わせた）
- **候補の線:** `b1 > −0.020` とした（66C の要素の層の判定と同じ「δ を超える」）
  - 背景の文（bg-v2 の推定用）のベクトルは、生成が動くときに一度だけ作って保存する。本番は off なので作らない
- **生成のきっかけ:**
  - 登録の後（文のベクトルを作るジョブの最後）・欠かせない要素の切り替えの後・開いたとき（足りない分だけ）
  - 「候補が変わったとき」は、新しい人の登録のきっかけで、その人が関わる両方の向きを作ることで覆う
- **予算があふれたとき:** subject の順に作り、上限で止める（点の高い順に選ばない）
- **古い版（superseded）の扱い:** 開いたときに作り直す。作り直せない（上限）ときは、古い版をそのまま出す
  - 古い版も確かめは通っている
  - 「新しい版を出す」が作れるまでの間の扱いとして、こうした
- **承認済みの「承認時の説明」:**
  - 二人の読む欄が承認の後に変わったら、日付の後に「いまのプロフィールとは違うところがあります」と出す
  - 仕様の「違う欄を併記」は、欄ごとの差までは出していない
- **同意:** 新しい同意の版（§4-5）が決まるまで、誰も同意していない扱いにした
  - そのため、生成のバックエンドを入れても、本番では誰の説明も作られない
  - テストは同意を差し替えて確かめる
- **「縛られているもの」:** 仕組み（入力・確かめ・鍵）だけを作った。マイページの切り替え（§4-3）は確認の後の PR
  - 許可の関数は、いまは常に「使わない」を返す
- **目的の種類:** §4-4 の仮の規則を、生成の入力に使っている（下の §4 で確認を取る）
