## 1. 禁則抵触の有無／推測で補完した箇所

**禁則抵触: なし**
- 照合の計算・閾値・門・上層の印（保留のまま）・下層の一覧（閉じたまま）は変えていない
- 構造化の経路は変えていない。説明の生成は、登録された公開の文を読むだけ
- 外部の AI の API は使っていない（テスト 421 で確かめる）
- 数値を画面と公開 API に出さない
- 生テキスト・根拠・evidence_span・要約文・背景・経験・意志_なぜは、入力に使わない
- 段階1 の画面・描き方・確かめ（`src/explanation.py` の check()）の振る舞いは変えていない。生成の分の確かめは、別の関数に足した
- 既存の台帳のイベントは変えていない。台帳には何も書いていない（合意のイベントは §4-2 の確認の後）
- 本番の生成は止めたまま（`POX_EXPLANATION_BACKEND` の既定は off）。本番（Render）で fixed・local にすると起動しない

**推測で補完した箇所**
- **プロンプトの埋め方:** 仕様のプロンプトの `{N の目的・…}`・`{O の与え像・…}`・`{目的の参照・…}` の 3 か所を、型付きの JSON で置き換える
  - 記号 `{N}`・`{O}` はそのまま残す
  - sha256 は置き換える前のファイルの中身で取る（段1 `92f1a316…`・段2 `19f3bdc7…`）
- **出すかどうかは機械が決める（仕様 §4-1）:**
  - モデルの `status` は、not_covered と言ったときだけ従う（落とす方向にだけ）
  - explained かどうかは、確かめを通った組と、入力の欠かせない要素の印から決める
  - 欠かせない要素の印は、モデルの出力ではなく入力から取る（§12-4 の 13）
- **① の確かめに落ちたとき:** その目的は出さない（段階1 の check() と同じ扱い）
- **as-of:** 二人の読む欄の内容ハッシュにした（`h:<sha256>`）
  - プロフィール全体や版の番号ではなく、説明が読む欄だけ（仕様 §8-2 の考え方に合わせた）
- **候補の線:** `b1 > −0.020` とした（66C の要素の層の判定と同じ「δ を超える」）
  - 背景の文（bg-v2 の推定用）のベクトルは、生成が動くときに一度だけ作って保存する。本番は off なので作らない
- **生成のきっかけ:**
  - 登録の後（文のベクトルを作るジョブの最後）・欠かせない要素の切り替えの後・開いたとき（足りない分だけ）
  - 「候補が変わったとき」は、新しい人の登録のきっかけで、その人が関わる両方の向きを作ることで覆う
- **予算があふれたとき:** subject の順に作り、上限で止める（点の高い順に選ばない）
- **古い版（superseded）の扱い:** 開いたときに作り直す。作り直せない（上限）ときは、古い版をそのまま出す
  - 古い版も確かめは通っている
  - 「新しい版を出す」が作れるまでの間の扱いとして、こうした
- **承認済みの「承認時の説明」:**
  - 二人の読む欄が承認の後に変わったら、日付の後に「いまのプロフィールとは違うところがあります」と出す
  - 仕様の「違う欄を併記」は、欄ごとの差までは出していない
- **同意:** 新しい同意の版（§4-5）が決まるまで、誰も同意していない扱いにした
  - そのため、生成のバックエンドを入れても、本番では誰の説明も作られない
  - テストは同意を差し替えて確かめる
- **「縛られているもの」:** 仕組み（入力・確かめ・鍵）だけを作った。マイページの切り替え（§4-3）は確認の後の PR
  - 許可の関数は、いまは常に「使わない」を返す
- **目的の種類:** §4-4 の仮の規則を、生成の入力に使っている（下の §4 で確認を取る）

### 4-1. §4-2 台帳のイベントの設計（案）

**(1) 正準形 `a1` と `pair_digest`**
- 中身（JCS＝既存の `canonicalize` で正準化する）:
  ```
  {"canon_version": "a1", "relation_rule_version": "rel-v0.3",
   "need_subject": <申請者>, "offer_subject": <受けた人>,
   "purposes": [{"purpose_id": ..., "necessity_c4": <その目的の必要像の版の c4 ハッシュ>,
                 "pairs": [{"need_element": "1-2",                        # 必要像の文の番号
                            "need_quote_h": HMAC(鍵, 必要像の句),
                            "offer_ref": "offer.2" | "state.できること_型" | "interest.1",
                            "offer_version": <与え像の版のハッシュ（offer_hash）／現状・関心の欄の内容の HMAC>,
                            "offer_quote_h": HMAC(鍵, 相手の文の句),
                            "relation": "R2"}]}]}
  ```
  - 申請者の向き（申請者の目的 × 受けた人の文）で、explained の目的の組だけを入れる
  - ① は入れない。数値・プロフィール全体のハッシュも入れない
  - 組の並びは（目的の並び、必要像の番号、相手の参照）で固定する
- `pair_digest = HMAC-SHA256(POX_EXPLANATION_DIGEST_KEY, canonicalize(a1))`

**(2) 鍵付き**
- 句のハッシュと `pair_digest` は HMAC にする。短い日本語の句は、素のハッシュだと総当たりで戻せるため
- 鍵の識別子（`digest_key_id`。段階1 の render_digest と同じ鍵・同じ識別子）を添える
- 鍵を替えた後の確かめには、段階1 と同じく `POX_EXPLANATION_DIGEST_KEY_PREV` を使う

**(3) 新しいイベント `explanation.agreed`**

## 5. 1 日の生成の上限の既定値と、その理由

- **既定 50 向き／日**（`POX_EXPLANATION_DAILY_LIMIT`）。1 向き＝段1・段2 の 2 回の生成で、成否によらず 1 と数える
- **理由:**
  - 本番は off なので、上限が効くのは開発・計測（local）のとき
  - 手元の CPU の小さなモデルでは、1 向きに数分かかる（§3）。50 なら半日以内に収まる
  - いまの登録者の数では、1 人の登録で作る向き（その人が関わる候補の両方向）は、50 に届かない見込み（推測）
  - 段階3 で推論サーバーにしたら、計測の結果を見て見直す
