## 3. §3 正準形と版の設計（ここで止まる）

### 3-1. `種類` を必要像の正準形に入れる（c5）

- **入れる。新しい版 `c5` にする。** 目的ごとの項目なので、目的ごとの必要像のハッシュ（c4）が自然
- c5 の中身:
  ```
  c4 と同じ（必要像の文の配列 [{文, 必須, 型}]・数値 {gate_s, gate_u}・根拠のコミットメント・与え像のハッシュ）
  ＋ "種類": "補完" | "共鳴" | null
  ```
  - `null` は「本人が選んでいない」（rev4 以前の JSON を新しく登録したとき）
  - 読むときは、null を仮の規則（指示書69 §4-4）で補う
  - ハッシュには「選んでいない」をそのまま残し、選んだ値と区別する
- 本体の DB: 必要像の行に `種類` の列を足す（目的の選び直しの別の表は使わない。§5）
- 台帳: `necessity.published` の payload の `canon_version` が `"c5"` になる。ほかの項目は変えない

### 3-2. `説明への使用` をプロフィールの正準形に入れる（p4）

- **入れる。新しい版 `p4` にする。** 本人の選択で、説明の出し方に効くため
- p4 の中身:
  ```
  p3 と同じ（目的の向かう先・手段・関心・現状 4 欄・表示用の項目・意志_なぜ・経験）
  ＋ "説明への使用": {"縛られているもの": true | false | null}
  ```
  - `null` は「答えていない」（rev4 以前の JSON）。読むときは false として扱う
- 本体の DB: v5 の本文（`profile_v5.doc_json`）にそのまま入る。説明の生成はここから読む
- 台帳: `profile.structured` の payload の `canon_version` が `"p4"` になる

### 3-3. 古い版（rev4 以前）の登録の扱い

- **過去の版のハッシュは変えない。** c3・c4・p2・p3 で書いたイベントと行は、その版の規則のまま確かめる（いまと同じ仕組み）
- これから登録する v5 の JSON は、rev4 以前の形でも c5・p4 で書く
  - 無い項目は `null`
  - 「新しく書くものは最新の版」という、これまでの決まり（c3→c4・p2→p3 のとき）と同じ
- 読むとき:
  - `種類` が無い（null・c4 以前の行）→ 仮の規則（指示書69 §4-4）
  - `説明への使用` が無い → false（使わない）
- rev4 以前の JSON の受け付けは、今までどおり（`_meta.source` に `v5r5-A`・`v5r5-B` を足すだけ）

### 3-4. 台帳仕様 v2 §1-2-6（記録項目の意味を後から変えない。追加はできる）に照らして
