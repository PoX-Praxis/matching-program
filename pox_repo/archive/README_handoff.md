# 引き継ぎパッケージ — ②マッチング・メカニズム（PoX）

このZIPは、別チャットでこのプロジェクトを続けるための一式です。
**別トークの冒頭で、まず本READMEと `matching_spec_v0.4.md` を読んでください。**
それだけで、これまでの設計判断と現在地が把握できます。

---

## 0. 30秒サマリ
人間の「文脈→目標→手段→その手段を担える人材」という列を、LLMの中核操作
（意味ベクトル化・attention・系列予測）の発想で照合し、「目的を共有でき、
互いの不足を補える人／コミュニティ」を高精度に接続する仕組み（PoXのマッチング・エンジン）。

設計の本体は **`matching_spec_v0.4.md`**。このファイル単体で文脈が伝わるように書いてある。

## 1. 同梱物と読む順番
1. **`matching_spec_v0.4.md`** … 設計の本体（自己完結ブリーフ）。最初に読む。冒頭に版差分要約あり。
2. **`demo_walkthrough.md`** … Claudeが全層を手で代行した「仮マッチングの実演」の記録と再現手順。
3. **`github_transition_builder.py`** … 遷移テーブル構築器（本番用・要GITHUB_TOKEN）。実装・検証済み。
4. **`matching_engine_verify.py`** … (3)系列予測層→(4)照合層 の結線検証（意味類似度を正解注入）。設計の確定版。
5. **`matching_engine.py` / `matching_engine_v2.py`** … 上記に至る試行（設計過程の記録。失敗の経緯＝設計判断の根拠）。

## 2. いま確定していること（v0.4時点）
- 核心二操作の「実装上の正体」：attention＝LLMによる重み付き集約／予測＝初期は集計事前分布＋LLM推論（仕様2.1節）。
- 噛み合いは二チャネル（類似＝対称／相補＝非対称）。合算重みで用途別に切替（4.5節）。
- マッチング単位は二段階：個人＝必要を推測（遷移テーブル主役）／コミュニティ＝必要を宣言（AIは補足）（4.6節）。
- 外部接続は人間主導フロー。外部データは当面「遷移テーブルの統計材料」に限定、拡張は型互換性のみ確保（4.7節）。
- embeddingの目的＝意味比較＋スケール。仮・少人数なら意味比較はLLM代行で足り、embeddingは多人数化後（5.5節）。
- (3)→(4)結線は検証済み。要素別マルチベクトル化／翻訳層(3.5)の必須性も確定（5章・8.5節）。

## 3. 次の着手候補（別トークでやるとよい順）
- **(c) 要素別ベクトル化の最小実装**：既製embeddingを繋ぐ。本番フェーズの入口。
  → 環境はネットワーク制限が緩く、embeddingモデルを取得できる環境が望ましい。
  → `matching_engine_verify.py` の「正解注入していた類似度」を本物のembedding出力に差し替える形。
- **(a) 残る2データ源の実装**：共著論文・スタートアップ経緯を同じ「接続イベントの型」で集計。
  → `github_transition_builder.py` を雛形に横展開。新しい設計判断はほぼ不要。
- **(d) 接続成否ログのスキーマ確定**：PoX定義「行動が変わった瞬間」を記録する形を先に固定（8章の宿題）。後から変えると過去データが死ぬ。
- **(e) コミュニティの「宣言」入力フォーマット設計**：自然言語で受けてAI構造化か、半構造化フォームか（11章の新規未解決）。

## 4. 未解決の問い（11章より）
- 接続成否ラベルの取得方法（自己申告／行動変化の観測）。ネット断片は代理指標まで。
- コミュニティの宣言の入力フォーマット。
- 初期ユーザーの集め方（エンジン外の問題：広報・コミュニティづくり）。

## 5. 別トークでの再開手順
1. このZIPを解凍し、全ファイルを別チャットにアップロード。
2. 「`matching_spec_v0.4.md` を読んで現在地を把握して。続きとして〔(c) or (a) など〕をやりたい」と伝える。
3. コードを動かす場合、`github_transition_builder.py` は無料のGitHub個人アクセストークンを
   `export GITHUB_TOKEN=...` で与える（公開データ読み取りは無料・60→5000回/時に増える）。
