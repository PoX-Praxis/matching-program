# 接続成否ログ 仕様 v1.0 — 「接続」の定義と台帳

> 仕様書 v0.5 の **12章-5（成否ラベルの取得方法＝最大の急所）** と **12章-1（ログスキーマ確定）** への回答。
> ここでは **接続の定義のみ** を扱う（トークン分配・フェーズ判定・離脱検知のロジックは対象外）。

## 1. 接続の定義
- **器（コミュニティ）は一人でも作れる**が、それは「待機状態」であって接続ではない。
- **接続が成立するのは二人以上が相互承認して器に集まった時**。最初の相互承認が最小の器（二人）を生む。
- よって「器のない人と人の接続」は別立てしない（最初の接続＝最小の器）。

## 2. 記録単位 ＝「器への一参加」
- 単位は人と人のペアではなく **器への一参加（join）**。
- 成立条件は **新規参加者 ⇄ 器 の二方向承認**（器→新規、新規→器）。
- 二者・多者・既存コミュニティへの引き込み（v0.5 4.7節）を **すべて同じ型** で表せる。
- 完全グラフ（全員が全員を承認）は要求しない。誰が誰を承認したかは有向の承認集合として残すので、後から個別ペアの分析は可能。

## 3. 成否ラベル ＝ 動線上で必ず通る相互承認
「行動の前に相互承認が必要なように設計する」ことで、成否を観測した代理指標ではなく **構造的に必ず通る関門** にする。ループの中に正解が二段で並ぶ：

```
器を作る（一人でも可）              ＝ 待機。ラベルなし
   │
   ▼
2人目以降が ⭐️相互承認して加わる    ＝ 接続成立（弱い正解）  established_at
   │
   ▼
選択肢を合意して行動                 ＝ 何をしたか           action
   │
   ▼
結果を見て次の選択肢を ⭐️合意       ＝ 行動が変わった瞬間   advanced_at
                                       （強い正解 / PoX本来の成功）
   │
   └──────→ 次のループへ（フェーズが一段進む）
```

- **弱い正解**（接続成立）でコールドスタートを抜ける。
- **強い正解**（行動変化）が溜まったら学習をそちらへ寄せる（v0.5 8章の二段構造に一致）。

## 4. 記録の開閉
- レコードは **1つ目の⭐️で開き、2つ目の⭐️で閉じる**（`opened_at` → `closed_at`）。
- 結果が出るには時間がかかるので **開いたまま** 持てる（`terminal_state: active`）。
- 閉じないまま放置されたレコードは「接続したが行動に至らなかった」＝価値のある負例として残す（生存者バイアス対策）。

## 5. 箱だけ用意し、ロジックは後回し
- **終端状態**：現状 `active` / `advanced` のみ運用。`dissolved`（解散）/ `left`（離脱）は **値を予約するだけ**、検知ロジックは後実装。離脱は強い正解の裏返し（負例）なので、箱を今開けておかないと後で失敗データが死ぬ。
- **貢献の帰属**（`contributions`）：誰が接続に貢献したか（紹介・引き込み・承認・創設）を残す。成否分析に要る観測情報であり、**将来トークン分配を載せる接続点**。分配ロジック自体は本仕様では書かない。

## 6. 7.1節「接続イベントの型」への変換
台帳の各 `join`（established_at あり）を ⟨①接続前の文脈・フェーズ / ②接続した相手の特徴 / ③その後の状態変化⟩ へ変換する。③は代理指標ではなく確定事実：`advanced`→前進(+)、`dissolved`/`left`→立消え(−)、`active`→判定保留。検証済み（`validate_and_convert.py`）。

## 7. このスコープに **含めない** もの（明示的に切り離し）
- トークンの分配メカニズム（別レイヤー。台帳が先、分配は後。承認に報酬を直結させると正解ラベルが汚染される＝v0.5 12章-7 の悪用耐性）。
- 離脱・解散の検知ロジック（箱だけ用意）。
- フェーズ判定の方法（v0.5 12章-2。誰がどう①〜⑤を判定するか）。
