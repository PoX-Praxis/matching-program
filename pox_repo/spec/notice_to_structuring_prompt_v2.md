# 【通達】構造化プロンプト v2 への要求仕様 — マッチング側 v0.6 で確定した入力要件

> 宛先：構造化プロンプト v2 を担当するチャット／担当者
> 発信：②マッチング・メカニズム（PoX）担当。仕様 v0.6 にもとづく。
> 目的：マッチング側の入力要件が固まった（仕様9章の依存方向＝**本仕様が入力要件を決める → 構造化プロンプトがそれに合わせる**）。これは v2 を作り直す依頼ではなく、**反映すべき差分だけ**を伝える通達です。下の「要求項目」を v2 の出力（特に Layer A と②統合用素材）が満たすように調整してください。

---

## 0. 背景（なぜ通達するか）
マッチング側で、構造化情報を入れたら接続が返る最小エンジン（`matching_engine_live.py`）が動いた。その入力規格が、そのまま v2 への要求になる。加えて、接続成否ログ（相互承認トリガー）の確定により、v2 が埋めるべき項目が一つ明確になった（フェーズ）。**この2点が今回の差分の核心。**

## 1. 反映必須の差分（これだけは必ず）

### 差分A：フェーズ（①〜⑤）を Layer A の必須要素として出力する ★最重要
- マッチング側はフェーズを**判定しない**。**v2 が本人合意のうえで Layer A の一要素として構造化して渡す**ことに決定（v0.6 12章-2 の解決）。
- 値は次の5択（PoX フェーズ表＝仕様7章）。内部キーは英語、表示は日本語でよい：
  - `idea`（①アイデア：やりたいが形がない）
  - `mvp`（②MVP：試したい）
  - `early_validation`（③初期検証：ユーザーが欲しい）
  - `scale`（④スケール：拡大したい）
  - `fundraising`（⑤資金調達：金が必要）
- **本人が選ぶ／本人合意で確定**するのが原則（AIは推定を補助してよいが、決めるのは本人。4.6節の「宣言が主・推測が従」と同じ思想）。
- 確信が持てない場合は **null 許容**（マッチング側スキーマも null を受ける）。ただし null だと遷移テーブルが引けず必要像が出ないので、極力埋めること。

### 差分B：②統合用素材の4項目を、下記の最小規格に合わせる
マッチングエンジンの入力規格は、実マッチャ検証で使った形（通称「Aの形」）に確定。v2 はこの4項目を**判断を加えず抽出だけ**して出す（従来方針どおり）：

| 項目 | 中身 | 備考 |
|---|---|---|
| 意志 | その人が実現したいこと（1〜2文の核） | 類似チャネル（対称照合）に使う |
| 求めている | 不足・欲しい手段／人材（1〜2文） | 相補チャネル（非対称照合）の起点 |
| 能力 | 自分が持っている強み・担えること | 相手に求めるものと区別する |
| フェーズ | 上記5択（差分A） | 系列予測層が遷移テーブルを引く鍵 |

- これらは **要素ごとに分離して**出すこと（1ベクトルに潰さない＝仕様5章「要素別マルチベクトル」）。
- 既存の「生テキスト・要約文・attention候補・系列素材」（仕様6章）は**そのまま維持**。今回の差分はそこに追加・整合させるもの。

## 2. 据え置き（今回は変更不要なもの）
- attention候補・系列素材の抽出方針は v2 のまま。重み付け・予測はマッチング側が担う（6章）。
- Layer A のその他要素（再現性の型／潜在的役割／文脈と条件／接続インターフェース）は維持。
- **本人合意のうえで出力する**という大原則は不変。フェーズも合意対象に含めるだけ。

## 3. 今回は対象外（誤って盛り込まないこと）
- **トークン分配に関する項目**：v2 に入れない。台帳側で「貢献の帰属」だけ記録する設計で、分配ロジックは未着手（承認に報酬を直結させると正解ラベルが汚染される＝12章-7）。v2 が分配用の項目を持つ必要はない。
- **接続成否ラベルの記録**：これはマッチング側の台帳（`connection_ledger.schema.json`）の責務。v2 は関与しない。
- **コミュニティの宣言フォーマット**：第二段（コミュニティマッチング）の入力で、個人向け Layer A とは別物（4.6節）。今回の通達は**個人マッチングの入力**に限る。コミュニティ宣言フォーマットは別途設計（12章-A）。

## 4. フェーズ更新の連携（将来の約束事）
接続ループが一周し前進したとき（台帳の2つ目の⭐️＝`advanced`）、その人のフェーズが一段進む。マッチング側はこの前進を検知できる。**将来的に、更新後フェーズを v2 側の構造化情報へ書き戻し、次回の構造化時に本人が確認する**動線を想定。今は「そういう更新が来うる」ことだけ認識しておけば足りる（実装は後）。

## 5. v2 側でやってほしいこと（チェックリスト）
- [ ] Layer A に `phase`（5択 + null許容）を本人合意で埋める導線を追加。
- [ ] ②統合用素材の出力に「意志／求めている／能力／フェーズ」を**要素分離**で含める。
- [ ] 上記が入った v2 の出力サンプルを1件作り、マッチング側へ戻す（`matching_engine_live.py` の `seeker` にそのまま入る形か相互確認＝統合フェーズの完了条件）。
